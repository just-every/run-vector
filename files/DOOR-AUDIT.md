# Permission and visibility writer audit

All routes use the real application role authority and current identity; none of the checks uses an application mock. The public-door tests mount createServerApp() in the Cloudflare Worker runtime with migrated local D1 and native sign-in/invitation flows.

| Door or writer | Authority and outcome |
| --- | --- |
| PUT /api/settings/teams/:id/permissions, root | teams.permissions: workspace Owner/Admin or Member who owns that team; ordinary Member 403 even with settings=all_members. Preserved. |
| PUT /api/settings/teams/:id/permissions, child | Previously dynamically chose teams.hierarchy and admitted ordinary Members. Changed to teams.permissions for every team. setTeamPermissions independently checks and transactionally fences the same current-role/team-owner authority before no-op or writes; retains child/parent hierarchy authority and graph/state fences. Both settings and planning are covered. |
| PUT /api/settings/teams/:id/hierarchy | Explicit settingsPermission/planningPermission already used teams.permissions in fix2. Audit also reproduced ordinary Member reparenting an inherited child from planning=team_owners to planning=all_members with 200. Changes in permission inheritance, the inherited source parent or effective permission values now use that same owner authority and its transaction fence. Identical current values do not permit a Member to redirect a child to a parent they own and widen it later. Ordinary workflow/hierarchy edits with no permission change retain their declared teams.hierarchy rule. |
| PUT /api/v1/teams/:id/hierarchy | Same changeHierarchy service as native; regression proves Member 403 and Owner 200 for inherited reparent and switching back to inherited permission values. |
| inheritedPermissionWrites | Internal descendant propagation only, reached from the permission-checked parent write or hierarchy write; uses hierarchy graph fence and stays in the same commit batch. Child and descendant effective permissions tested. |
| PUT /api/settings/teams/:id/privacy | teams.privacy: Owner/Admin only; setTeamPrivacy includes an independent active Owner/Admin SQL guard and old privacy guard in its commit batch. Member refused regardless of parent or team settings. Existing role-matrix public-door probes cover roles and unchanged writes. |
| PUT /api/v1/teams/:id/privacy | Same teams.privacy row and setTeamPrivacy service; existing role-matrix session and API probes exercise both surfaces. No child-specific alternate row. |
| POST /api/settings/teams and POST /api/v1/teams | isPrivate=true resolves teams.privacy; ordinary team creation follows teams.create and the workspace creation setting. New child inherits parent's permissions under parent hierarchy authority and its creator is its initial team owner. Schema accepts no explicit permission value overrides. Existing team-membership and sub-team journeys cover current Member/Guest/Viewer refusals and Owner/Admin private creation. |
| PATCH /api/settings/teams/:id | Strict teamUpdateSchema omits isPrivate and parentTeamId and accepts neither permission field. No permissions or visibility writer. |
| PUT /api/settings/teams/:id/membership; membership decisions and members PUT/DELETE | teams.membership / teams.members rules; these change membership authority, not settings_permission/planning_permission/is_private. Existing role matrix and membership journey retain their assertions. |
| Archive restore / local source setup | Native HTTP archive restore is separately Owner-only; stopped local restore/setup has local resource custody, not Member session authority. No new permission route is exposed. Raw record restore remains covered by the existing archive and Owner gates. |
| Scoped API / agent doors | No independent /api/v1 team-permissions setter or agent mutation of these settings exists. Native team permission route rejects bearer-only admission; hierarchy and privacy API routes use current token authority and the shared services above. |

Search scope: all assignments and SQL updates/inserts of settings_permission, planning_permission and is_private in src/core/features; administration create/update schemas and routes; team membership permissions/privacy services and routes; sub-team hierarchy and propagation; integration API registrations; roles doors, matrix, policy and transaction fences. No unrelated UI, permissions policy table or clause judgment was changed.

Payload detail: the native permission route has a strict schema requiring both settings and planning. The reproducible valid request includes settings=all_members alongside planning=all_members, rather than the brief's abbreviated planning-only JSON. The reported 200 is an actual valid-payload permission escalation, not an inferred result for an invalid payload.
