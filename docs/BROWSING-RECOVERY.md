# Browsing and deletion recovery

Issue-list continuation uses an opaque `revision` string. Read `/api/issues` with offset zero and retain its response revision; send that exact string as the `revision` query parameter on every positive offset with the same normalized filters, sort, grouping and page size. The identity binds the workspace and its current calendar date as well as a conservative database revision. Any write to a browsing dependency invalidates continuation, even if it does not alter this particular filter's membership. The revision, bounded rows, total, grouping counts and board status counts are read in one D1 batch transaction.

A missing or obsolete continuation identity returns HTTP 409 with `error: "pagination_invalidated"` and a restart message, without issue rows or counts. Clients must discard that traversal and request offset zero. Issues, Board and saved-view browsers visibly restart at the first page. The revision is ephemeral transport state; it is never stored in saved-view definitions or operator preferences. Six sorts, seven groupings, filters and full-result aggregates retain their meaning.

After a successful board move, the destination column is selected and focus returns to its enabled status selector only after genuine refreshed rows arrive. If the issue leaves the active filters or bounded page, an accessible result explains the move and focuses its Open issue action. The browser does not change the operator's filters to force the card into the result.

Migration `0019_browse_revision_file_custody.sql` is additive after byte-identical migrations 0001–0018. It adds revision triggers and an independent `detached_file_removals` ledger. Validate the populated previous-schema upgrade before switching an installation. The later `0033_issue_deletion.sql` adds the public native operator command and its minimal receipt.

The native version-checked issue deletion service transfers every unresolved file reservation, including already-deleted metadata and in-flight writers, to that ledger in the same D1 transaction as discussion deletion, direct-child detach activities and version changes, and parent deletion. Grandchildren and identifiers survive. Native session and operator admission still guard the whole transaction. Any stale version, revoked admission or SQL failure leaves deletion effects absent.

R2 removal follows the committed intent. The genuine scheduled cleanup scans both ordinary and detached custody, deletes settled objects, checks absence and then confirms removal. An absent object with an unsettled writer remains pending indefinitely; elapsed time is not a writer fence. A matching original upload object or the original writer's completion settles its reservation. Failed deletes retain custody and charge bytes until confirmed. Quotas and operator-removal admission include detached unresolved files. Confirmed cleanup keeps an identifier-only audit receipt without restoring a deleted issue or discussion.

Back up D1 and R2 together and retain the matching source and migration receipts. On application rollback retain the additive schema, revision triggers, cleanup ledger and every unresolved reservation. Only code that discovers detached cleanup, settles its writers and includes its bytes in quota and operator-removal checks is compatible once custody has transferred. Do not deploy an earlier cleanup/quota reader against those records or reverse the migration. Validate restoration of a prior complete backup with its matching source in isolated resources before traffic changes. This is provider-backup recovery, not a new application export/restore facility.

`pnpm test:browse-review` exercises genuine local Worker/browser responses at desktop and mobile widths: empty-board keyboard access, delayed-refresh status movement, parent editor focus, persisted long view titles, list/board/saved-view restart, and actual scheduled cleanup discovery. Worker regressions cover transaction races, discussion dependencies, R2 failure, late writers, quota retention and populated migration. These are local correction checks; full verification, hosted delivery and wider product acceptance remain separate.
