# Managed source preparation

Vector vendors Base delivery-producer, owner-claim and editor source from the Base main revision recorded in [Base adoption](BASE-ADOPTION.md). `scripts/delivery/base/packaging.json` is the one packaging policy, selecting the same canonical `rer-setup.json` that local installation reads. The Base exporter adjusts only the producer setup-reader schema import locations; this exported adaptation is recorded in edition provenance, while exact runtime/schema copies are recorded by the existing source tool.

Run `rer build`, then `pnpm integration:sync` to regenerate the committed `management/integration/deployment-spec.json`, setup digest in `rer-project.json` and `.github/workflows/rer-managed.yml` from the Base producer. Verify runs `pnpm integration:check` after building and refuses drift. RER reads these files from the selected source revision for Managed Configure. `pnpm run artifact:delivery` produces the schema-2 Worker package without deployment. The workflow pins the reviewed trusted-build source to a full commit and is dispatch-only. Development sample data and the local mail outbox are restricted to loopback; hosted builds default to production mode without sample data. Managed mail uses the RER relay described below; Free and Assisted hosting retain their existing provider options. Owner claim and linked identity do not require mail.

## Managed mail

The deployment spec opts in with `mail: {providers: ["rer"]}`. The setup manifest declares public `MAIL_PROVIDER`, `MAIL_FROM` and `MAIL_RELAY_URL`, plus private `MAIL_API_KEY`; the key is required when the provider is `rer`. Managed Configure supplies these values and hides all four inputs. No mail-provider account or key entry is needed from the customer. `MAIL_PROVIDER` is `rer`, the relay URL is RER's `${APP_URL}/api/managed-mail/send`, and `MAIL_FROM` follows RER's platform sign-in sender policy. The relay uses the installation's app name as the sender display name. Free and Assisted retain direct-provider choices; owner-account deployment still uses the documented SendGrid path. Local setup defaults to the development outbox, which hosted Configure refuses: hosted plans must select a delivery provider and supply any key it requires.

On plan save, RER issues a random installation/environment credential, stores it with encrypted private settings and indexes only its hash at the relay. Vector receives that credential as `MAIL_API_KEY`; the underlying SendGrid key never reaches the app or its build. Settings readback returns secret names, not credential values. The pinned Base mail adapter sends a JSON `POST` to `MAIL_RELAY_URL` with `Authorization: Bearer MAIL_API_KEY`, `Content-Type: application/json` and `redirect: "error"`. Its body is `{to, subject, text, html?}`, with one recipient and no sender or installation ID. Authentication and notification mail use the same adapter without a Vector fork.

The relay accepts a nonempty subject of up to 200 characters without newlines, nonempty text of up to 65,536 characters, optional HTML of up to 65,536 characters and at most 128 KiB of JSON. HTTP 202 with `{accepted: true}` means provider acceptance, not inbox arrival. Errors distinguish invalid input (400/413), missing or retired credentials (401), unavailable paid access (402), inactive hosting or suspension (403), rate limiting (429 with `Retry-After` seconds), provider/network failure (502), and unavailable service configuration/admission (503). Vector applies its ordinary authentication failure and [notification delivery policy](NOTIFICATIONS.md); it never switches providers automatically.

Production and preview share an allowance of 20 messages per minute, 200 per hour and 1,000 per day per installation. Valid attempts consume allowance even if the provider fails; credential rotation does not reset it. The relay checks paid access and hosting state on every send, independently of AI credit. Scheduled cancellation retains service through the paid period; disconnect or effective exit revokes credentials.

The RER installation owner can rotate a production or preview credential through the same-origin `POST /api/delivery/installations/:id/mail/:environment` route, or revoke it with `DELETE` on that route. Neither returns the credential. Rotation invalidates pending releases: build and publish again to bind the replacement. Ordinary Configure saves preserve an existing credential and cannot revive an explicitly revoked one; renewed hosting after revocation requires explicit rotation. Local source checks do not establish hosted relay acceptance.

## Owner claim and editor

The signed owner claim uses deployment-controlled RER issuer, installation ID, exact application origin, canonical FIRST_OWNER_EMAIL and a public EC/P-256 key ring. SESSION_SECRET and the generated hidden SETUP_TOKEN remain server-only. A bare confirmation popup accepts the signed claim from its exact opener/issuer, waits for native POST, and creates an ordinary Base operator-auth owner/session. The permanent claim/bootstrap ledgers refuse another claim. Local setup and owner-account deployment use native `POST /auth/bootstrap` with `{token, displayName, returnTo}`: 303 creates the owner and opens `/setup`; 409 `already_initialized` keeps an existing owner. A configured token suppresses automatic owner creation until admission. Signed Managed configuration requires its signed claim and refuses the raw-token route. The deploy wrapper preserves Base's `managesHostedOwner` marker, so Base claims the token it deploys and retires it. Existing initialized and restored installations cannot be claimed again.

`/api/editor/config` requires the current native owner session, its admitted Vector identity and destination restore access. All Vector operators retain equal authority under OPS-001; this adds no product roles. Missing configuration returns 503, anonymous/revoked access 403, and non-GET requests 405. The response contains only enabled state, exact management origin, installation ID and a lease of at most 30 seconds. The owner shell renews through the server, revokes synchronously when sign-out starts or authorization is lost, and surfaces configuration/auth failures. Silent server revocation is observed by the short lease.

Compiled visual edits are installed before hydration from `src/editor/visual-edits.json`. Each rendered destination, including sign-in and NotFound, owns readiness; navigation pauses the same copied runtime. Owner teardown preserves published compiled edits. Application HTTP CSP retains unrelated script/nonces and limits frame-src and frame-ancestors to self and the configured exact management origin. The actual management service must independently authorize the installation and supply its registered application frame-ancestors.

Apply 0024 forward. Preserve existing owners, sessions, all prior SQL and permanent admission state. Keep additive ledgers on compatible-source rollback; validate matching-source backups in isolated D1/R2 resources before traffic changes. Restore excludes claim/session credentials and requires fresh configuration/access/effect review. Tests use ephemeral synthetic signing keys and a labeled local management peer; they cannot establish hosted editor/service acceptance.

After a successful claim, the owner reviews the workspace at `/setup` and completes setup through its public action before entering `/app`. Existing completed installations retain their completion stamp.

Stage installation, trusted hosted build/attestation, real service authorization/header behavior, live accounts, the public flip and homepage remain with the owner.

The editor configuration is admitted only for the recorded installation owner, with the current native Base session and destination restore grant rechecked before returning it. Invited operators retain equal product access and do not receive an editor mount or owner warning. The editor grant is non-secret and expires; this management admission does not introduce product roles.
