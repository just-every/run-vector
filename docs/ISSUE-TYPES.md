# Team issue types

Issue types are optional team configuration. Only a workspace Owner manages them, following ROLE-008's default for a door without a matrix row. Setting an issue's type uses the existing issue-edit permissions, including invited Guest access and Viewer refusal.

`PUT /api/settings/teams/:id/issue-types` accepts `{ "enabled": true }` or `{ "enabled": false }`. The first enable creates Bug, Feature, Task and Epic with stable identities and emoji icons. If the team already has a single-select Severity field, Bug requires that field by its definition ID. Disabling retains definitions, assignments and required-field associations and appends a retained-type activity entry on each typed issue. Re-enabling restores the same identities. Read metadata exposes choices only for enabled teams.

`PATCH /api/settings/teams/:id/issue-types/:typeId` accepts `expectedVersion` and one or more of `name`, `icon` or `requiredFieldIds`. A name is unique within its team; the icon is one emoji. Required fields must be single-select definitions of that team. Adding a requirement refuses if any existing issue of the type lacks a valid option. Renames do not rewrite issue values. Changes are audited and stale configuration is refused.

Native issue creation and editing accept nullable `issueTypeId`. An issue has at most one type of its own team. When choosing a type, supply every required field in the final `customFields` object. Clearing a required value, including by omitting it from that full object, returns 400 without issue, activity, follower, notification or identifier-reservation changes. Template application, scoped issue writes, bulk edits, copies and agent issue tools share the same admission. Database guards recheck the requirement in the committing transaction. A required value remains required while type controls are disabled.

Copies within the enabled source team retain the type. A copy to another team accepts an explicit destination `issueTypeId` and destination `customFields`; otherwise its `droppedValues` names the dropped type. Team moves also clear the team-owned type and retain its former identity in movement history. Undo retains the paired type and custom-field state and refuses an inverse that would violate a current requirement.

Issue lists accept `issueType=<type identity>`, `issueType=none` and `grouping=issueType`. Groups retain separate identities even when different teams use the same display name. Global group totals cover the full filtered result, and the query persists in saved views. Disabled teams project no active type in lists.

Jira All Fields CSV review accepts explicit `jira.issueTypes` choices, such as `{ "Story": "<Feature identity>", "Bug": "<Bug identity>" }`. Once this map is supplied, each nonempty source type needs a selected identity or an explicit null, which reports an omission. There is no name-based guessing. A required Severity column can be reviewed with `jira.customFields`, keyed by the field identity, each containing `column` and an `options` map from source values to option identities. Preview runs FIELD-001's shared admission; apply is bound to the reviewed mapping and final type availability. Reconciliation reports physical source rows, retained type choices and planned and written counts per type. The older untyped Jira profile retains its reported omissions and Epic label behavior until explicit type mappings are chosen.

Apply `0133_issue_types.sql` additively. Definitions, requirements, enabled state, assignments and issue history are portable domain data. Native snapshots omit an unset type so earlier import receipts retain their original shape. Restoration preserves disabled assignments and does not replay historical activity. Retain the schema on compatible rollback.

The backend and mounted-door proof are supplied here. Settings controls, issue editor and creation controls, list controls, reviewed import controls, their browser proof, and the required independent Claude Opus interface qualification remain outstanding. Per-type template and request-form integration, boards, insights, SLAs and the other importer obligations remain with their receiving clauses.
