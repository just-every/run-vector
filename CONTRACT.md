# CONTRACT.md — Vector

This is the product Vector is building towards, not a description of what ships today. Every clause has a stable ID, states the behaviour a buyer gets, names the acceptance evidence that proves it through a public door (a browser journey, an HTTP route, a command, a signed webhook, a built mobile app), and carries a status judged from the current code and tests: **done** (implemented and exercised by the cited test), **partial** (some of the behaviour exists at the cited file, the rest is open) or **missing** (no implementation yet). The status table at the end lists every clause. Difficulty — native apps, provider apps, coding-agent sandboxes, live syncs — is recorded as engineering work in a clause, never as a reason to drop it.

Security, privacy and operational requirements are in BASELINE.md, and no product clause supersedes a baseline clause. Capacity and rate limits in seed.json remain estimates; a stated latency is a target until measured. Clauses marked *Policy* name intended replaceable behaviour. Dated evidence distinguishes executed checks from unmet obligations.

## Scope

Vector is a full Linear/Jira-class issue tracker for software teams. A team that runs on Linear, Jira Software or GitHub Issues and Projects — or on the up-and-comers Plane and Huly — can move to Vector and keep doing the whole job: fast keyboard-first issues, triage, cycles, projects, initiatives and roadmaps; roles and private teams; reporting; mobile apps; follow-up automation; and the integrations the category runs on (GitHub, GitLab, Slack, Microsoft Teams, Zendesk, Intercom, Sentry, Figma, Notion and the coding agents). Work flows from report to merged change and on to a verified fix: an accepted issue can be delegated to a coding agent that opens a tested pull request under human review, the deployment is tracked, and the issue closes only when the user-facing problem is shown to be gone.

**Buyer.** A US software team of 5 to 500 people — engineering, product and design, with support and leadership as readers — replacing Linear, a Jira Software project or GitHub Projects. Self-hosted on the buyer's own Cloudflare account, free and open source; money appears only as customer revenue in USD (CUST-001).

**Separation from sibling products.** Vector keeps the market's separation and links to its siblings rather than rebuilding them:

- **Penny** owns the customer feedback board, public roadmap and public changelog (the Canny/Productboard job). Vector receives Penny requests as customer-request links on issues and hands shipped work back to Penny (CUST-001, CUST-003, RELEASE-003).
- **HappyToHelp** owns the support inbox, **Orbit** the CRM, **Spool** error tracking, **Uptime** external checks and **Oncall** paging. Vector links their records to issues and reads their evidence (CUST-001, ERROR-002, PUSH-004) but never replaces them.
- Cross-functional work management for non-software teams (the Asana, monday.com and ClickUp job) is not Vector's product; Vector is for software delivery.
- The code host, CI runners and deploy platform stay GitHub, GitLab, Bitbucket and the buyer's CI; Vector owns work state, relationships and delivery evidence.

**Scope before this contract** was one business workspace of equal operators built around evidence-led intake decisions, issues, work streams, projects, dated cycles, saved views, search, in-app notifications and Linear/Jira file imports, with integrations, AI, roadmaps, roles, chat, mobile and real-time collaboration declared out of scope. Those clauses remain where they still hold, rewritten where the scope changed, and now form one part of the full job.

## Workspace, people and permissions

- **OPS-001 — Workspace access.** Every workspace member sees and acts on every public team's issues, intake items, cycles, projects, initiatives, labels and shared saved views, and on every notification addressed to them; team membership organises work and, for a public team, never restricts access. Roles (ROLE-001), private teams (ROLE-002) and guests (ROLE-003) are the only rules that narrow access, and a private saved view (VIEW-002) is visible only to its owner. Every read, search result, notification, export, webhook, Slack unfurl, mobile payload, API response and agent context applies the same rule server-side. *Acceptance:* the existing equal-access tests plus a role-matrix journey that signs in as Admin, Member and Guest and checks every private route, `/api/v1` route, search and export against ROLE-001–003. *Status:* partial — `tests/worker/search-access.test.ts`, `tests/worker/removal-boundary.test.ts` (equal operators; roles, private teams and guests open).
- **SETUP-001 — First workspace review.** Fresh configured owners review their workspace at `/setup` before entering an app route. Signed-out visitors return there after ordinary sign-in. Only the recorded installation owner may complete setup through a same-origin, current-session transaction. Completion survives repeated setup, restart and local restore. Existing configured installations retain completion through the additive upgrade. *Acceptance:* `tests/worker/first-run.test.ts` (tests tagged SETUP-001). *Status:* done — `tests/worker/first-run.test.ts`.
- **OPS-002 — Operator management.** Operators are invited and removed in settings. The operator configured at setup can be removed only by themselves. *Policy: `operator.management.v1`; default: any operator may invite or remove.* *Acceptance:* `tests/worker/base-auth.test.ts` (tests tagged OPS-002). *Status:* done — `tests/worker/base-auth.test.ts`.
- **OPS-003 — Workspace time.** Settings hold one IANA workspace timezone. Every calendar day, due reminder, cycle start and end instant, and seven-day window named in this contract is evaluated in that timezone. Changing it never rewrites stored instants, closed cycle snapshots, or reminders already delivered. *Acceptance:* `tests/e2e/admin-workspace-time-journey.mjs`, `tests/e2e/admin-access-journey.mjs`, `tests/e2e/admin-runtime.mjs` (tests tagged OPS-003). *Status:* done — `tests/e2e/admin-workspace-time-journey.mjs`.
- **OPS-004 — Safe removal.** Vector rejects removal of the last operator. A successful removal revokes that operator's sessions, unassigns their non-terminal issues, transfers each project they lead and each shared saved view they own to the operator performing the removal — or to the longest-standing remaining operator when they removed themselves — deletes their private saved views and their notifications, anonymises their references in retained comments, activity, and audit records, and writes one activity entry per changed issue and project. *Acceptance:* `tests/worker/removal-boundary.test.ts`, `tests/e2e/collaboration-runtime.mjs`, `tests/worker/base-auth.test.ts` (tests tagged OPS-004). *Status:* done — `tests/worker/removal-boundary.test.ts`.
- **ROLE-001 — Workspace roles.** Each member has exactly one role: Owner, Admin, Member or Guest. Owners and Admins invite and remove members, change roles, manage teams, workflows, integrations, API tokens, automations, agents and workspace settings; Members create and change work in the teams they can see; Guests act only inside the teams they were invited to (ROLE-003). The installation owner is an Owner and the last Owner cannot be demoted or removed. Every role change is audited (ROLE-005) and takes effect on the member's next request, including open sessions and API tokens. *Acceptance:* a browser and HTTP journey in which an Admin promotes and demotes a Member, the demoted member's next settings request returns 403, and the last-Owner demotion is refused. *Status:* missing.
- **ROLE-002 — Private teams.** An Admin can make a team private. Its issues, comments, attachments, cycles, triage, project memberships and search entries are visible only to its members and to Owners; a project or initiative that spans a private team shows other viewers only the counts they may see, never titles. Making a team public or private is audited and re-evaluates notifications, followers, Slack channel routes and webhooks. *Acceptance:* a journey that creates a private team, proves a non-member gets 404 on its issue by identifier, sees no search hit, no Current entry and no export rows, then is added and sees all of them. *Status:* missing.
- **ROLE-003 — Guests.** A Guest (a contractor, agency or customer engineer) is invited to named teams only, sees only those teams' issues and projects, cannot see the member directory beyond those teams, cannot create API tokens or integrations, and is labelled as a guest wherever they appear. *Acceptance:* a guest journey that reaches only the invited team and is refused every other team, settings and token route. *Status:* missing.
- **ROLE-004 — Single sign-on and provisioning.** Owners can require SAML 2.0 or OpenID Connect sign-in through Okta, Microsoft Entra ID or Google Workspace, restrict sign-up to verified company domains, and provision and deprovision members through SCIM 2.0; deprovisioning revokes sessions and tokens and applies OPS-004. *Acceptance:* a journey against a local SAML/OIDC identity-provider fixture at the network edge that signs a member in, then a SCIM `DELETE` that revokes their session within one request. *Status:* missing.
- **ROLE-005 — Audit log.** Owners and Admins can browse, filter and export as CSV a workspace audit log of sign-ins, role and membership changes, team privacy changes, integration and token changes, automation and agent runs, exports, imports and deletions, each with actor (person, automation, integration or agent), time, action and subject. Entries survive subject deletion with an opaque reference and are never editable. *Acceptance:* a journey that performs one action of each kind and finds each in the audit view and the CSV. *Status:* partial — `src/core/features/administration/transaction.ts` (audit entries are recorded; there is no audit view, filter or export).
- **ROLE-006 — Apps and agents as actors.** Integrations, automations and coding agents act under their own named identities with explicit scopes, never as a person. Their changes show the app or agent name with the person who installed or delegated to it, and they can be paused or revoked by an Admin at once. *Acceptance:* a journey that installs an agent identity, sees its change attributed to it in activity and audit, revokes it and sees its next API call refused. *Status:* missing.

## Teams and workflows

- **TEAM-001 — Team identity.** A team has a name and an identifier prefix, each unique across archived and non-archived teams. The prefix is two to ten uppercase letters and cannot be changed once the team has an issue, so existing identifiers stay resolvable. Every issue belongs to exactly one team. *Acceptance:* `tests/e2e/admin-team-journey.mjs` (tests tagged TEAM-001). *Status:* done — `tests/e2e/admin-team-journey.mjs`.
- **TEAM-002 — Team workflow.** Every team has an ordered list of workflow statuses with at least one status in each of the Intake, Backlog, Unstarted, Started, Completed, Canceled, and Duplicate categories, and status names unique within the team. Operators can add, rename, and reorder statuses; a status never changes category, and no category is added or removed. A team's *default status* in a category is the first status of that category in workflow order, and every clause naming a category as a destination moves the issue there. *Acceptance:* `tests/e2e/admin-team-journey.mjs`, `tests/worker/base-auth.test.ts` (tests tagged TEAM-002). *Status:* done — `tests/e2e/admin-team-journey.mjs`.
- **TEAM-003 — Team archiving.** Archiving a team stops new issues, intake, and issue moves from targeting it while preserving its issues, cycles, projects, identifiers, and history; a signal source request naming an archived team creates nothing and returns 409. Unarchiving restores normal use. Teams are never deleted; archiving is the only terminal state. *Acceptance:* `tests/e2e/admin-archive-team-journey.mjs` (tests tagged TEAM-003). *Status:* done — `tests/e2e/admin-archive-team-journey.mjs`.
- **TEAM-004 — Status removal.** Removing a workflow status requires a destination status in the same category and atomically moves every issue to it. Vector rejects removal of a category's last status and records the status mapping in audit history. *Acceptance:* `tests/e2e/admin-team-journey.mjs` (tests tagged TEAM-004). *Status:* done — `tests/e2e/admin-team-journey.mjs`.
- **TEAM-005 — Team settings.** Each team chooses whether it uses triage, cycles and estimates; its estimate scale (points 1–100 as ISSUE-011, Fibonacci, exponential or T-shirt sizes mapped to points); its default issue template; its triage responsibility (TRIAGE-001); its Git automation rules (GITHUB-003); and its auto-close and auto-archive periods (AUTO-003). Turning a feature off hides it for that team without deleting history. *Acceptance:* a settings journey that switches a team to T-shirt estimates and off cycles, then sees the issue editor and Current reflect it while closed cycle snapshots stay unchanged. *Status:* missing.

## Issues

- **ISSUE-001 — Creation.** An operator can create an issue with a required title and team plus an optional Markdown description, assignee, project, cycle, priority, labels, estimate, due date, expected outcome, customer impact, and custom fields. It starts in the team's default Backlog status unless another non-Intake status is explicitly chosen. *Policy: `issue.defaults.v1`; default: unassigned, no priority, no cycle, and no project.* *Acceptance:* `tests/e2e/core-runtime.mjs`, `tests/markdown-rendering.test.tsx` (tests tagged ISSUE-001). *Status:* done — `tests/e2e/core-runtime.mjs`.
- **ISSUE-002 — Stable identifiers.** An issue identifier is its team's prefix, a hyphen, and an integer one higher than the highest ever allocated under that prefix, so a number is never reused after an issue is deleted. The identifier never changes, including when the issue moves teams (ISSUE-012); a prefix therefore records where an issue started, not where it lives. *Acceptance:* `tests/worker/issue-deletion-relations.test.ts` (tests tagged ISSUE-002). *Status:* done — `tests/worker/issue-deletion-relations.test.ts`.
- **ISSUE-003 — Priority.** An issue has exactly one priority: Urgent, High, Medium, Low, or No priority. No priority is the default and sorts after Low. *Acceptance:* A test that sets each of the five priorities and checks that No priority is the default and sorts after Low. *Status:* partial — `src/core/features/issues/input.ts` (implemented; no test names the clause yet).
- **ISSUE-004 — Status transitions.** A version-checked operator mutation (ISSUE-006) can move an issue in any direction among the Backlog, Unstarted, Started, Completed, and Canceled statuses of its team's workflow. Vector rejects moving any issue into an Intake status. Leaving Intake uses INTAKE-005, INTAKE-007, or REL-003; entering or leaving Duplicate uses REL-003 or REL-005. Entering Completed records the completion time and entering Canceled records the cancellation time; leaving one of those categories clears the time it recorded and removes no activity. *Acceptance:* `tests/worker/issue-session-projection.test.ts` (tests tagged ISSUE-004). *Status:* done — `tests/worker/issue-session-projection.test.ts`.
- **ISSUE-005 — Assignment.** An issue has at most one assignee. Assigning, reassigning, or unassigning it takes effect immediately and records the actor, the previous assignee, and the new assignee. *Acceptance:* `tests/worker/removal-assignment.test.ts` (tests tagged ISSUE-005). *Status:* done — `tests/worker/removal-assignment.test.ts`.
- **ISSUE-006 — Concurrent edits.** Every issue carries an integer version that increases by one on each mutation that appends an activity entry under ISSUE-007. An issue mutation carries the version the client last read; if the stored version is higher, Vector rejects the mutation with 409 and returns the current issue and version, changing nothing. Adding a comment, evidence revision, follower, or notification does not change the version and is never rejected as stale. *Acceptance:* `tests/e2e/core-runtime.mjs`, `tests/e2e/collaboration-preferences.mjs`, `tests/worker/dependencies.test.ts` (tests tagged ISSUE-006). *Status:* done — `tests/e2e/core-runtime.mjs`.
- **ISSUE-007 — Activity history.** Creation and every change to title, description, team, status, priority, assignee, project, cycle, estimate, due date, labels, expected outcome, customer impact, custom fields, duplicate target, parent, or dependency append an immutable activity entry recording the time, the previous value, the new value, and the actor — the operator, or the named automation when a cycle closure, deferral return, or import acted. *Acceptance:* `tests/worker/dependencies.test.ts`, `tests/e2e/admin-label-journey.mjs`, `tests/worker/cycle-closure.test.ts` (tests tagged ISSUE-007). *Status:* done — `tests/worker/dependencies.test.ts`.
- **ISSUE-008 — Comments.** Any operator can add a Markdown comment, and can edit or delete any comment; the entry records who acted. An edited comment shows its edit time. Deleting a comment removes its body, attachments, links, and search entry, leaves a tombstone and an activity entry in the thread, and does not remove the follower state it created. *Acceptance:* `tests/worker/discussion-access.test.ts`, `tests/e2e/collaboration-runtime.mjs`, `tests/e2e/core-runtime.mjs` (tests tagged ISSUE-008). *Status:* done — `tests/worker/discussion-access.test.ts`.
- **ISSUE-009 — Attachments and links.** Operators can attach files and named HTTPS links to an issue or a comment. Removing either records the action; removing a file also deletes its blob under `BASE-DATA-003`. *Acceptance:* `tests/worker/discussion-file-admission.test.ts`, `tests/e2e/core-runtime.mjs`, `tests/worker/link-cascade.test.ts` (tests tagged ISSUE-009). *Status:* done — `tests/worker/discussion-file-admission.test.ts`.
- **ISSUE-010 — Deletion.** Deleting an issue removes its comments, attachments, links, evidence revisions, dependencies, parent link, follower state, notifications, activity, and search entry; its children become root issues, and a duplicate is removed from its canonical issue's list. Vector rejects deleting a canonical issue that still has duplicates. Closed cycle snapshots (CYCLE-005) and audit entries keep only its identifier, and its source idempotency records (INTAKE-002) are retained so a re-delivery cannot resurrect it. *Policy: `issue.can-delete.v1`; default: any operator.* *Acceptance:* `tests/worker/issue-deletion-cascade.test.ts`, `tests/worker/collaboration-atomicity.test.ts`, `tests/worker/issue-deletion-import.test.ts` (tests tagged ISSUE-010). *Status:* done — `tests/worker/issue-deletion-cascade.test.ts`.

- **ISSUE-013 — Mentions.** Typing `@` in an issue description or comment offers matching operators, and choosing one records a mention of that operator. ## Relations

- **REL-001 — Dependencies.** An operator can record that one issue blocks another, across teams, and can remove the link. Vector rejects self-links, a link that already exists in either direction, and any link that would create a directed cycle. *Acceptance:* `tests/worker/dependencies.test.ts` (tests tagged REL-001). *Status:* done — `tests/worker/dependencies.test.ts`.
- **REL-002 — Blocked state.** An issue is shown as blocked while any issue that blocks it is outside a Completed, Canceled, or Duplicate category. Blocking never changes the issue's workflow status by itself. *Acceptance:* `tests/worker/dependencies.test.ts` (tests tagged REL-002). *Status:* done — `tests/worker/dependencies.test.ts`.
- **REL-003 — Duplicate decision.** Marking an issue as a duplicate requires one canonical issue that is neither itself nor already a duplicate, moves it to the team's default Duplicate status, and preserves its description, comments, evidence, attachments, and activity under the duplicate issue. *Acceptance:* `tests/worker/issue-deletion-relations.test.ts` (tests tagged REL-003). *Status:* done — `tests/worker/issue-deletion-relations.test.ts`.
- **REL-004 — Canonical duplicates.** A canonical issue lists every direct duplicate. If it is later marked duplicate, Vector atomically repoints its duplicates to the new canonical issue, so a duplicate chain or cycle is never exposed. *Acceptance:* `tests/worker/issue-deletion-relations.test.ts` (tests tagged REL-004). *Status:* done — `tests/worker/issue-deletion-relations.test.ts`.
- **REL-005 — Undo duplicate.** Undoing a duplicate decision removes the canonical link and restores the issue's most recent non-terminal status, or its team's default Backlog status if it has none, while preserving both decision activity entries. *Acceptance:* `tests/worker/issue-deletion-relations.test.ts` (tests tagged REL-005). *Status:* done — `tests/worker/issue-deletion-relations.test.ts`.
- **REL-006 — Parent and child.** An issue has at most one parent. An operator can set, replace, or clear it from issue details. Vector rejects self-parenting and ancestry cycles; changing a parent never changes status, team, project, cycle, or assignee, and deleting a parent makes each direct child a root issue. Issue lists can filter to roots or to children of one exact parent (VIEW-001). *Acceptance:* `tests/worker/issue-deletion-preimage.test.ts`, `tests/worker/parent-deletion-custody.test.ts` (tests tagged REL-006). *Status:* done — `tests/worker/issue-deletion-preimage.test.ts`.
- **REL-007 — Related issues.** Members can mark two issues as related across teams, with no blocking effect; the link shows on both issues, survives team moves, imports from Jira "Relates" and Linear "related" links when both issues are in the run, and is removed when either issue is deleted. *Acceptance:* a journey that relates two issues, sees both sides, and a Jira import fixture whose in-run Relates link becomes a related link. *Status:* missing.

## Intake and triage

- **INTAKE-001 — Intake creation.** A registered signal source (INTAKE-011) creates an intake issue with a title, team, observed time, its source ID, source display name, source record identifier, source revision identifier, summary, link, and optional structured measurements and customer reports. An operator creates one with a title and team and any of the same descriptive fields, attributed to that operator instead of a source. Either way it starts in the team's default Intake status and appears in Needs decision (CURR-002) within 5 seconds. *Acceptance:* `tests/worker/source-ingest.test.ts`, `tests/e2e/core-runtime.mjs` (tests tagged INTAKE-001). *Status:* done — `tests/worker/source-ingest.test.ts`.
- **INTAKE-002 — Idempotent sources.** Re-delivery of the same source ID, source record identifier, source revision identifier, and normalised payload returns the original result and creates nothing. Re-delivery of an identity whose issue has since been deleted (ISSUE-010) returns 410 and creates nothing. Reusing an identity with a different payload returns 409 and changes nothing. *Acceptance:* `tests/worker/source-ingest.test.ts`, `tests/worker/source-erasure-identity.test.ts` (tests tagged INTAKE-002). *Status:* done — `tests/worker/source-ingest.test.ts`.
- **INTAKE-003 — Evidence revisions.** A new source revision identifier for an existing source record appends immutable dated evidence even when revisions arrive out of order. The issue orders evidence by observed time, then receipt time, and shows a field-level change from the preceding observed revision. *Acceptance:* `tests/worker/source-ingest.test.ts` (tests tagged INTAKE-003). *Status:* done — `tests/worker/source-ingest.test.ts`.
- **INTAKE-004 — Inspectable assessment.** An intake issue shows the evidence behind its attention reason, impact measurements, likely cause, recommended assignee, suggested priority, suggested labels and likely duplicates. Each assertion names whether it came from a source, an operator, a policy or an agent; an agent assertion also names the model, the records it read and when, and is shown as a suggestion until a person accepts it. Vector never presents an inferred assertion as a fact or applies one silently. *Acceptance:* the existing operator-intake journey plus a triage journey in which an agent suggestion is shown with its provenance and is applied only on acceptance. *Status:* partial — `tests/e2e/core-runtime.mjs` (source, operator and policy provenance; agent provenance is open with TRIAGE-003).
- **INTAKE-005 — Accept.** Accepting an intake issue atomically records the actor, the time, and an optional reason; applies the chosen assignee, priority, cycle, and Started or Unstarted status; and clears any deferral. It leaves Needs decision and reaches its new Current and My work sections within the CURR-008 window. *Acceptance:* `tests/e2e/core-runtime.mjs` (tests tagged INTAKE-005). *Status:* done — `tests/e2e/core-runtime.mjs`.
- **INTAKE-006 — Defer.** Deferring an intake issue records the operator, an absolute return time strictly in the future, and an optional reason, and removes it from Needs decision. It returns there exactly once — within 5 minutes of the return time, or within 5 seconds of a new evidence revision (INTAKE-003), whichever comes first — and the return atomically clears the deferral and leaves the earlier decision visible. ## Honest boundaries

Vector does not do these jobs, and buyers get them as follows (US-first):

- **Code hosting, CI runners and production deploys.** Vector links to GitHub, GitLab or Bitbucket and the buyer's CI and deploy platform (GitHub Actions, CircleCI, Vercel, Cloudflare); it never hosts repositories, runs builds or deploys.
- **Running coding agents.** Agents run in their providers' sandboxes (Claude Code, OpenAI Codex, Cursor, GitHub Copilot) or the buyer's own runners; Vector holds delegation state, context and evidence, never source checkouts or production credentials inside its Worker.
- **Customer feedback board, public roadmap and changelog.** Penny.
- **Support inbox, CRM, error tracking, uptime checks, paging.** HappyToHelp, Orbit, Spool, Uptime and Oncall, or Zendesk, Intercom, Front, Salesforce, HubSpot, Sentry, Datadog and PagerDuty through the integrations above.
- **Cross-functional work management for marketing, operations and agencies.** Not Vector's product (Asana, monday.com or ClickUp); Vector serves software delivery.
- **Wiki and design tools.** Vector has project documents and specs (PROJ-013) but is not a company wiki or design tool; it links Notion, Confluence, Google Drive and Figma.
- **Timesheets, billing and capitalised-labour reports.** Not provided; buyers use Harvest, Toggl or Clockify linked by issue identifier, and REPORT-005 exports for finance.
- **Enterprise service management (help-desk ITSM, change approval boards) and regulated validation.** Not provided; an issue status is not a legal approval or a compliance record. Buyers use Jira Service Management or ServiceNow alongside.
- **Perpetual parity with every incumbent field and app.** Imports report every omission, and transition syncs (DATA-016) are bounded; Vector does not promise ongoing two-way parity with Jira or Linear.
- **App-store publication.** The iOS and Android apps (MOBILE-001) are built from source; publishing them under the buyer's Apple and Google developer accounts, or using a Run Edit Run build, is a release step outside the installation.
